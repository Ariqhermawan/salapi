# Salapi — Security & Honesty Guidance

This project is a crypto-invisible peso/rupiah fintech PWA on Stellar
(`salapi-blond.vercel.app`). Real money will move through the contracts
once mainnet anchors land, so the safety bar is higher than a typical
web app. Review with these project rules on top of the built-in
vulnerability checklist.

## Honesty spine (non-negotiable)

- **Kocok / draw randomness.** The winner of any Arisan or Paluwagan
  round MUST come from a contract call's return value
  (`arisanKocok`, `paluwaganCollect`). Never `Math.random()` for
  winner selection. Roulette animations may use timer-driven motion
  for visual decoration, but the FINAL landing index must equal the
  contract-returned winner address (see `ArisanRoomScreen.tsx`).
- **No fabricated data.** Never hardcode pool figures, fake tx
  hashes, fake user addresses, or simulated balances. Day-30
  features = LIVE on-chain real. Preview features carry visible
  "Pratinjau · Build-Award" framing.
- **Honest preview chips.** Preserve `TESTNET VERSION`, `SANDBOX`,
  `Pratinjau` chips where they exist. Removing or hiding them
  silently is a deception. Localising them is fine; user may
  intentionally keep some English ("TESTNET" is a universal tech term).
- **No misleading on-chain claims.** If a flow is sandbox (e.g.
  `/topup`, `/withdraw` anchors), copy must say so. Don't move
  "sandbox" labels off-screen for visual cleanup.

## Crypto-invisible UX

- No raw Stellar wallet addresses in user-facing UI. Mono-font
  contract IDs in `/transparency` are the only allowed exception
  (users opt in to inspect the chain there).
- No seed phrases anywhere. The signer model is custodial; users
  never see keys.
- Show peso / rupiah / dong only via `Money` / `Peso` components from
  `@/components/ui/kit` — they're currency-aware and respect the
  user's display-currency preference. Don't hardcode `₱`, `$`,
  `Rp `, `₫` directly in JSX.
- Never log signers, secrets, private keys, or seed material in
  console output. Server-side signer material stays server-side.

## Soroban / Stellar contracts

- Every state-mutating function in a Soroban contract must call
  `host.require_auth()` / `member.require_auth()` (or the appropriate
  caller's `require_auth`) before any token transfer or persistent
  storage write.
- **Storage footprint must be deterministic.** Soroban's `env.prng()`
  cannot drive storage keys (e.g. `RoomByCode(code)`) or token
  transfer destinations, because simulation and execution would see
  different values and trap with "outside the footprint." Use the
  client-supplied-value-verified-on-chain pattern (see `arisan_rooms`
  `kocok()` accepting `winner_idx: u32`).
- Contract IDs live in `web/.env.local` only — never hardcoded in
  app source. The `BASE_VAULT_CONTRACT`, `DISASTER_CONTRACT`,
  `PALUWAGAN_CONTRACT`, `SMART_SAVINGS_CONTRACT`,
  `ARISAN_ROOMS_CONTRACT`, `USERNAME_REGISTRY_CONTRACT` env vars are
  the source of truth.

## Server actions / signer hygiene

- `invokeAs(secret, ...)` — the `secret` argument must come from
  `getSigner()` or one of the `FRIENDS[].secret()` accessors on the
  server. Never accept a Stellar secret from a request body, query
  string, header, or user input.
- Server actions return `{ ok: boolean, link?: string, error?: string
  | errorKey?: string }`. Errors must be human-readable / locale-keyed
  — don't leak raw contract error codes (`Error(Contract, #11)`) or
  stack traces.
- Use `readContract(id, method, args)` for reads (simulate, no
  signature) and `invokeAs(secret, id, method, args)` for writes
  (sign + submit + poll). Never mix.

## i18n (build will fail if violated)

- Every new `t("key")` must exist in all four locales: `en`, `tl`,
  `id`, `vi` (see `web/lib/i18n/dictionaries.ts`).
  `type Dict = typeof en` enforces this at compile time, so the
  Next.js build fails if a locale is missing a key.
- Never add a user-visible string without going through `t()`. Strings
  that are technical artifacts (contract names like `paluwagan`,
  `base-vault`) stay as literals.

## Commit hygiene

- Never `git add -A` or `git add .` — the working tree has many
  intentionally untracked artifacts (audit docs, prompt files, design
  briefs, pitch deck PDFs, snapshot JSONL, build outputs). Stage by
  path, by hand.
- Build must be green (`cd web && npx next build`) before every
  push. If `EPERM … unlink '.next/…'` on Windows OneDrive,
  `rm -rf .next` then rebuild.
- Never `--no-verify`, `--no-gpg-sign`, or otherwise bypass commit
  hooks. If a hook fails, investigate and fix the underlying issue —
  don't create a new commit that amends or bypasses.
- Don't commit `.env`, anything containing real Stellar secrets, or
  files generated by automated tools (lighthouse reports go to the
  repo; runtime caches don't).

## PWA + layout

- The manifest (`web/app/manifest.ts`) icons array must list PNG
  variants BEFORE the SVG so Android launchers don't fall back to a
  generic "S + dot" badge. PNG assets are sourced from
  `Salapi-Logo-Kit/`.
- The bottom nav must stay anchored to the viewport. The contract is:
  the outer wrapper uses `h-svh overflow-hidden`; `main` uses
  `flex-1 overflow-y-auto pb-[calc(env(safe-area-inset-bottom,0px)+80px)]`;
  the `TabBar` uses `position: absolute; bottom: 0` with
  `paddingBottom: calc(env(safe-area-inset-bottom, 0px) + 16px)`.
  Don't break this when restructuring layout or screens.

## Pre-existing audit context

The 200-persona PWA test (`PERSONA-TEST-REPORT.md`) flagged real
trust signals to preserve and real concerns to address. When changing
copy or UI, check whether your change moves the app toward or away
from the persona-grounded honest framing. The biggest cross-cutting
findings:
- `/transparency` 6-contract list is the trust spine — preserve it
- Anti-bodong messaging on Arisan ("kontrak yang pegang pot, bukan
  bandar") directly answers a major user fear
- Don't compound testnet/sandbox/preview chips into a panic wall
- Custodial signer with no key-export caps trust for tech-savvy
  users — flagged as future work, not a current bug

When introducing new features, ask whether they're day-30 LIVE or
Build-Award preview, and label accordingly.
